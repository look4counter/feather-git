### QA-001 — 선택한 저장소와 실제 이력 변경 대상이 다름

**위치**: [수정된 공통 명령 구성](../src/repository.rs:431), [Reset](../src/commit_history_actions.rs:250), [Revert](../src/commit_history_actions.rs:218)

**재현 조건**: 같은 작업 폴더의 .git과 .git2에 동일한 두 커밋 A, B가 있고 양쪽 HEAD와 인덱스가 B를 가리킨다.

1. .git2를 열어 B가 현재 HEAD임을 확인하는 요청을 만든다.
2. 앱의 reset_commit(.git2, A, Soft)를 호출한다.
3. 반환 결과와 각 Git 디렉터리의 HEAD를 비교한다.

**기대**: .git2의 HEAD만 A가 되고 .git은 B를 유지한다.

**실제**: 함수가 성공을 반환하지만 .git2는 B를 유지하고 **.git의 HEAD가 A로 바뀐다**. Revert(B, 커밋 안 함)도 성공을 반환하면서 .git2의 인덱스는 그대로 두고 .git의 인덱스에 notes.txt 삭제를 스테이지했다.

**추가 재현**:

- 작업 폴더에 .git2만 있고 상위에도 저장소가 없으면 정상적인 대상 커밋이 있어도 `not a git repository`로 실패한다.
- 상위 폴더에 별도 .git 저장소가 있으면 **상위 저장소의 HEAD가 이동하는 경우도 재현했다**. 선택한 하위 .git2는 바뀌지 않았다.

**원인**: 검증은 open_exact(.git2)로 수행하지만 명령은 `git -C <workdir>`만 사용한다. GIT_DIR·GIT_WORK_TREE를 제거하면서 --git-dir/--work-tree를 전달하지 않아 Git이 다른 저장소를 탐색한다.

**영향**: 선택하지 않은 저장소의 이력과 인덱스를 조작한다. Soft로 직접 재현했으며, 같은 명령 구성 경로를 쓰는 Hard 모드에서는 작업 파일 손실 위험도 있다. **Hard 손실 자체는 실행하지 않았다.**

**동일 패턴 추가 위치**: [병합 중단](../src/synchronization.rs:84), [리베이스 중단](../src/rebase_actions.rs:302). 이 두 동작은 코드상 같은 결함이 확인됐으나 이번 재현 도구로 중단 동작까지 직접 실행하지는 않았다.

**권장 조치**: 모든 Git CLI 호출에 선택한 repo.path와 repo.workdir을 명시적으로 전달하고 외부 Git 환경변수의 영향을 통제한다. .git2 단독·동일 부모의 .git/.git2·상위 저장소가 있는 경우를 Reset/Revert/각 continue·abort에 걸쳐 검증해야 한다.

### QA-002 — 검색에 Git 메타데이터가 섞임

**위치**: [작업 파일 검색](../src/repository_search.rs:117), [미추적 파일 수집](../src/repository_search.rs:151)

**재현**: .git과 .git2가 함께 있는 작업 폴더의 .git을 열고 원본 search 함수로 `.git2`를 검색한다.

**기대**: Git 내부 파일은 작업 파일 검색 결과에서 제외된다.

**실제**: `.git2/HEAD`, `.git2/config`, `.git2/index`, `.git2/objects/...` 등 **32개 내부 파일**이 검색 결과에 포함됐다.

**원인**: 변경 파일 목록에는 다른 Git 디렉터리 제외 처리가 있지만 검색은 libgit2의 미추적 파일 목록을 별도로 순회하면서 같은 제외 규칙을 사용하지 않는다.

**영향**: 검색이 내부 파일로 오염되고, 저장소 설정·객체 파일을 작업 파일처럼 열게 할 수 있다. 토큰·개인정보 노출은 이번 테스트에서 재현하지 않았다.

**권장 조치**: 현재 및 동위 Git 메타데이터를 제외하는 규칙을 작업 파일 검색에도 적용하고 일반 파일·일반 하위 저장소와 구분해 회귀 검증한다.

### QA-003 — 터미널에서 선택 저장소 컨텍스트 상실

**위치**: [PowerShell 구성](../src/workspace_backend.rs:681), [Git Bash 구성](../src/workspace_backend.rs:741), [호출](../src/workspace_backend.rs:749)

**조건**: .git과 .git2가 같은 작업 폴더에 있고 앱에서는 .git2를 선택한다.

**코드상 동작**: 실제 작업 폴더로 current_dir만 지정하고 선택한 Git 디렉터리를 환경변수나 명령 인수로 전달하지 않는다.

**CLI 재현**: 그 작업 폴더에서 `git rev-parse --absolute-git-dir`를 실행하면 선택한 .git2가 아니라 **.git**이 반환됐다. 실제 PowerShell/Git Bash 창을 조작하여 재현한 것은 아니다.

**영향**: 사용자가 앱에서 선택한 저장소라고 생각하고 터미널 Git 명령을 실행하면 다른 저장소에 적용할 수 있다.

**권장 조치**: 터미널을 선택 저장소 컨텍스트로 열거나, 단순 작업 폴더만 여는 동작이라면 사용자에게 어떤 저장소가 선택되는지 명확히 안내한다. 외부 터미널 동작은 별도 실사용 확인이 필요하다.

### QA-004 — 숨김 Git 디렉터리 선택의 사용성 위험

**위치**: [Open 폴더 선택 요청](../src/ui.rs:2453), [Windows 파일 대화상자 옵션](../vendor/gpui/src/platform/windows/platform.rs:909)

**코드 확인**: Create·Clone은 Git 디렉터리를 숨기지만 Open은 폴더 선택을 요구한다. 네이티브 대화상자는 FOS_PICKFOLDERS 등을 설정하며 FOS_FORCESHOWHIDDEN은 설정하지 않는다.

**위험**: 숨김 항목 표시가 꺼진 Windows 환경에서는 .git/.git2를 목록에서 찾기 어려울 수 있다. 경로 직접 입력은 가능하므로 열기 자체가 불가능하다고 단정하지 않는다.

**검증 수준**: 환경 의존 코드상 위험이다. 실제 폴더 선택창 접근이 막혀 화면에서 재현하지 못했다.

**권장 조치**: 숨김 Git 디렉터리 선택을 지원할 UI 정책을 정한 뒤 숨김 표시가 꺼진 Windows에서 직접 검증한다.

## 테스트 통과가 보장하는 범위

기존 자동화는 생성·복제·열기, 기본 저장소의 커밋·브랜치·이력 변경, Merge/Rebase 충돌과 중단, Stage/부분 Stage, 파일 이력, 세션·최근 목록·삭제 보호, UI 상태와 비동기 요청 처리를 검증했다. UI 상태 단위 테스트는 실제 앱 화면 조작과 다르다.

전체 테스트가 통과했지만 QA-001과 QA-002는 기존 테스트에 없던 사용자 지정 저장소의 후속 동작에서 재현됐다. 따라서 전체 통과만으로 출시 준비 완료라고 판단할 수 없다.
