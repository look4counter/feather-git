# 검증 결과: 히스토리 최적화와 그래프 간격

## 구현과 요구사항 대응

- FR-001: old의 uniform_list/범위 processor 방식으로 변경했다. Workspace::history는 전 행을 생성하지 않고 요청받은 표시/측정 범위만 history_row로 렌더링한다.
- FR-002~003: 프로젝트별 HistoryState에 토폴로지, 세로/가로 스크롤과 선택적 준비 행을 보관한다. 제목/작성자/날짜/해시/참조의 SharedString 및 RowGraph는 처음 필요한 행만 생성하고 재사용한다. 높이 측정용 0번 행 호출 때문에 다른 준비 행을 지우지 않는다.
- 탭 전환은 기존 캐시를 유지하고 스냅샷 교체만 해당 프로젝트 캐시를 무효화한다. 탭 닫기는 해당 캐시를 해제한다. 세로 핸들 재사용과 가로 위치 유지/스냅샷 교체 시 초기화를 테스트했다.
- FR-004~005: 레인 압축을 제거하고 중심 간격 20px/최소 중심 여백 10px로 배치한다. 레인 수에 따라 graph_width를 늘리고 최소 45px는 유지한다. 헤더/행에 같은 너비를 적용하며 표 전체를 공통 가로 스크롤로 감싼다. Shift+휠/가로 스크롤 입력은 기존 GPUI Windows 처리를 사용한다.
- FR-006: GraphBuilder 알고리즘, 부모 관계/색상, 24px 높이와 확대된 체크아웃 원/픽셀 보정은 유지했다. 기존 좁은 열 압축 테스트는 사용자 요청에 따라 변경된 열 확대/고정 간격/노드 경계 테스트로 대체했다. 기대 겹침 조건을 완화하지 않았다.
- Git 로딩/정렬/200개 상한과 Dialog/IME/시작 탭 동작 및 외부 의존성을 변경하지 않았다. 명세의 FR-001~006과 코드가 일치한다.

## 재현과 자동화

- 수정 전 원 간격 회귀 테스트는 45px 고정 열과 기존 레인 간격에서 실패했다.
- 수정 후 1~64개 레인과 100/125/150/175/200% 배율에서 확대 체크아웃 노드끼리도 최소 4px 여유가 있고 열 경계 안에 있음을 확인했다.
- 10,000개 합성 이력에서 25개 표시 범위와 측정용 1개만 준비하고, 같은 범위 재요청에 문자열 캐시를 공유함을 확인했다. 빈/범위 끝/과도한 범위도 검증했다.
- cargo fmt --check, cargo check --offline: 통과.
- cargo test --offline: 47개 통과, 성능 측정용 2개 ignored. 이 2개도 별도 명령으로 모두 통과했다.
- cargo clippy --offline --all-targets: 통과. 기존 탭 테스트 field_reassign_with_default와 GPUI 부동소수점 미래 호환성 경고가 남아 있다.
- cargo rustc --offline --bin feather-git -- -o target/debug/feather-git-history.exe: 통과. 기존 proc-macro-error2 미래 호환성 및 링크/출력 경로 안내가 있다.

## 성능 측정

동일 환경/테스트 프로필의 합성 이력 준비 코드 측정이다. GUI 레이아웃/실제 프레임 시간이나 FPS 측정이 아니다. 단일 실행 관측값으로 절대 성능을 보장하지 않는다.

| 측정 작업 | 수정 전 또는 전체 준비 | 변경 후 표시 범위/캐시 |
|---|---:|---:|
| 200개 커밋의 워밍업 후 프로젝트 전환 1,000회, 동일 select_project 호출 | 349,502µs | 186µs |
| 200개 이력의 초기 표시 데이터 준비, 동일 HistoryState 함수 | 전체 200행 319µs | 표시 25행 33µs |
| 10,000개 합성 이력의 초기 표시 데이터 준비 | 전체 10,000행 13,268µs | 표시 25행 46µs |
| 준비된 25행의 반복 범위 요청 1,000회 | 비교 기준 없음 | 200개 이력 2,394µs / 10,000개 이력 2,141µs |

첫 행의 전/후는 실제 Workspace 프로젝트 선택 경로를 수정 전후 같은 입력/호출 수로 측정한 값이다. 나머지는 새 준비 함수의 전체/표시 범위 작업량 비교이며 이전 전체 GUI의 속도라고 해석하지 않는다.

## 미검증 범위

기존 화면 도구 실행 파일 사용 승인 제한으로 실제 GPU 프레임/스크롤 반응, 가로 헤더 정렬과 시각적 간격을 직접 확인하지 못했다. 사용자가 체감한 지연의 모든 원인을 해결했다거나 실제 FPS 개선률을 측정했다고 주장하지 않는다. 초기 로딩 상한은 기존처럼 200개이며 추가 페이징은 이번 범위 밖이다.

## 수직선 GPU 경로 제거 검증

- 수직선은 vertical_bounds의 직접 quad를 사용한다. 경로 캐시 생성은 수직선을 건너뛰고 곡선만 보관한다. 단일 레인 직선 이력의 그래프 Path 생성은 0이다.
- 새 테스트 작성 시 미구현 함수로 실패를 확인했다. 구현 후 분수 배율의 Y 경계 테스트에서 실패하여 Y 끝점을 물리 픽셀 경계로 정렬했다. 테스트 조건은 유지했다.
- cargo fmt --check, cargo test --offline(48개 통과, 수동 성능 측정 2개 제외), cargo clippy --offline --all-targets, cargo build --offline 통과. 기존 GPUI float fallback, 기존 테스트 초기화 스타일, 의존성 미래 호환 및 링커 안내 경고는 남아 있다.
- 주요 변경: src/history_graph.rs와 본 기능의 명세·계획·작업·조사·검증 문서. Git 데이터 계층, 그래프 토폴로지, 의존성과 공용 렌더러 변경 없음.
- 수렴 점검: FR-007/SC-005의 직접 사각형, 곡선 보존, 배율 경계는 구현과 일치한다. FR-001~006의 가상 목록·캐시·간격 구현은 유지한다. 추가 코드 불일치 없음. 실제 GPU 프레임 시간 및 창 이동·스크롤의 체감 개선은 T007에서 계속 미검증이다. 기존 컴퓨터 사용 도구의 실행 파일 사용 승인 제한으로 실제 UI 검증은 수행하지 않았다. 사용자 문제가 완전히 해소되었다고 판정하지 않는다.

## old 렌더링 동등화 결과

- src/history_graph.rs: old history_view.rs의 수직선 채움/곡선 스트로크 생성 블록을 동일하게 적용했다. 원은 old의 네 개 베지어 PathBuilder 구현을 가져왔다. 선 경로 캐시 → 선 페인트 → 외원 → HEAD 내원 순서로 통일했다. 이전 직접 quad 구현은 사용자 동등화 요청으로 대체했다.
- 원 크기와 선명도 요구는 node_geometry의 물리 픽셀 경계로 유지한다. 20px 레인과 24px 행도 유지한다. 따라서 좌표/크기는 이전 요구를 따르며 old와 픽셀 단위 전체 화면 동일성을 주장하지 않는다.
- src/ui.rs: 중첩 h_full을 flex_1으로 바꾸고 old scroll_frame처럼 flex_1/min_h_0/min_w_0/overflow_hidden으로 목록 뷰포트를 제한했다. 헤더와 목록의 공통 가로 스크롤은 유지한다.
- 검사: cargo fmt --check, cargo test --offline(48개 통과, 수동 성능 측정 2개 제외), cargo clippy --offline --all-targets, cargo build --offline 통과. 기존 upstream float fallback 및 기존 테스트 초기화 스타일 경고, 의존성 미래 호환 경고는 남아 있다. 새 collapsible_if 경고는 수정 후 재검사했다.
- 수렴: FR-008/009 및 SC-006의 코드 조건을 대조했으며 구현 누락과 모순 없음. FR-007/SC-005는 새 사용자 요구로 대체되었으므로 더 이상 현행 quad 수용 조건으로 사용하지 않는다. 기존 가상 목록/프로젝트 캐시는 유지한다.
- 미검증: 실제 GPU 프레임 시간, 창 이동·스크롤 체감 및 시각 회귀는 T007에서 계속 추적한다. 앞서 컴퓨터 사용 도구의 실행 파일 사용 승인 제한이 있었으며 이번에도 실제 UI를 조작하지 않았다. 사용자가 보고한 느림이 해소되었다고 판정하지 않는다.
- 비교 조건: 현재 사용자는 cargo run(debug), 조회된 old 프로세스는 target/release 실행 파일이다. 실행 프로필이 다른 상태에서 성능 동등성을 주장하지 않는다. 이번 변경은 Cargo 프로필을 바꾸지 않는다.

## 실제 프레임 계측과 개발 빌드 최적화

문제: 기존 수정은 실제 프레임 비용을 검증하지 못했으며 사용자는 계속 느림을 보고했다. 최종 정상 코드 변경은 Cargo.toml의 gpui/taffy 개발 프로필 설정이다. GPUI opt-level=3 및 debug-assertions=false, taffy opt-level=3을 적용했다. 앱 자체 검사와 release 설정은 유지했다.

측정: 앱 내부 반복 렌더 테스트를 임시로 구성했다. 숨겨진 1440×900 창, 200개 선형 합성 이력, 기본 화면을 반복 생성하고 Window.draw 이후 요소 arena를 매 프레임 정리했다. Windows present를 직접 호출했다. 61개 프레임 중 초기 5개를 제외한 56개를 집계했다. 동일 코드와 같은 데이터에 대해 프로필 설정만 바꿨다. 첫 시도의 arena 미정리 측정은 최종 근거에서 제외했다.

| 지표 | 기존 개발 설정 | GPUI/taffy 최적화만 | 최종 설정 |
| --- | ---: | ---: | ---: |
| UI 준비 중앙값 | 16.9995ms | 10.1705ms | 5.8100ms |
| UI 준비 95백분위 | 46.357ms | 17.385ms | 7.717ms |
| 배치/prepaint 중앙값 | 10.4835ms | 7.4220ms | 4.2630ms |
| DirectX 호출 중앙값 | 0.2655ms | 0.3055ms | 0.0940ms |

최종 UI 준비 중앙값은 약 65.8% 감소했다. 목록 표시 요청은 전체 200개 중 14개이며 측정용 0..1 콜백 두 번도 확인했다. GPU 경로 40개/배치 8개는 최종 테스트에서 유지했다. GPU 호출 시간은 비동기 GPU 완료나 실제 화면 FPS를 뜻하지 않는다. 숨겨진 창, 합성 데이터, 강제 전체 갱신 테스트이므로 실제 사용자 저장소/입력 스크롤/창 이동의 프레임 지연으로 일반화하지 않는다. 원시 로그는 target/frame-probe-final-before.log, target/frame-probe-final-after.log, target/frame-probe-no-inspector.log에 있다.

임시 UI/Window/DirectX 계측, 자동 반복 실행 및 합성 데이터는 모두 제거했다. 정상 소스에서 FEATHER_FRAME_PROBE/PROBE 문자열이 없음을 확인했고 DirectX 렌더러는 old와 텍스트가 동일하다. 기존 공개 데이터 및 렌더링 모양은 변경하지 않았다.

최종 검사: cargo fmt --check, cargo test --offline(48개 통과, 수동 벤치마크 2개 제외), cargo clippy --offline --all-targets, cargo build --offline 통과. 기존 upstream float fallback, 기존 테스트 초기화 스타일 및 미래 호환/링커 안내 경고는 유지된다.

수렴: FR-010/011, SC-007과 T014~T017의 구현·측정을 대조하여 누락 없음. 임시 진단 제거 조건 충족. 헌장은 미작성 템플릿이다. 기존 실제 사용자 스크롤/시각 검증 T007은 여전히 미완료이므로 사용자 증상의 완전한 해소로 판정하지 않는다. 이번 실행은 앱 자체 렌더 테스트이며 외부 UI 조작은 수행하지 않았다.
