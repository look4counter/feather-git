# 기능 명세: 조회 완료 후 입력 차단 해제

**작성일**: 2026-11-03
**상태**: 검토 완료
**입력**: 사용 중 여러 기능이 반응하지 않고 재시작하면 복구되는 문제를 수정한다.

## 사용자 시나리오와 검증

### 사용자 이야기 1 — 조회가 겹쳐도 계속 작업하기 (우선순위: P1)

사용자는 새로고침 중 검색 결과의 커밋을 선택한 뒤에도 조회가 끝나면 태그 추가, 병합, 설정 등 기존 기능을 계속 사용할 수 있다.

**우선순위 이유**: 남은 작업 중 상태가 앱 전체 입력을 막는다.
**독립 검증**: 새로고침과 커밋 선택을 겹치게 실행하고 완료 순서를 바꿔 입력 차단이 해제되는지 확인한다.

**인수 시나리오**:

1. 새로고침 중 커밋을 선택하고 새로고침이 먼저 완료되면, 커밋 조회는 계속되고 모든 조회 완료 후 입력 차단이 해제된다.
2. 커밋 조회가 먼저 완료되어도 새로고침 완료 후 입력 차단이 해제되며 선택한 커밋은 유지된다.
3. 새로고침이 실패해도 다른 조회로 대체된 작업의 차단 상태는 해제된다.

### 사용자 이야기 2 — 최신 조회 보호 (우선순위: P2)

사용자는 연속으로 새로고침해도 이전 요청의 완료 때문에 최신 조회의 작업 중 표시가 사라지거나 화면 내용이 덮어써지지 않는다.

**우선순위 이유**: 진행 중 작업의 보호를 유지해야 한다.
**독립 검증**: 두 새로고침의 완료 순서를 바꿔 최신 작업만 차단을 해제하는지 확인한다.

**인수 시나리오**:

1. 두 번째 새로고침이 진행 중일 때 첫 번째가 완료되어도 두 번째의 작업 중 상태는 유지된다.
2. 두 번째가 먼저 완료된 후 첫 번째가 완료되어도 최신 결과와 해제된 상태가 유지된다.

### 경계 조건

- 닫힌 탭의 결과를 적용하지 않는다.
- 다른 탭의 실제 히스토리 조회가 진행 중이면 기존 입력 보호를 유지한다.
- 성공과 실패 모두 동일한 완료 정리 규칙을 따른다.

## 요구사항

### 기능 요구사항

- **FR-001**: 다른 조회로 대체된 새로고침도 완료 시 자신이 남긴 작업 중 상태를 해제해야 한다.
- **FR-002**: 오래된 요청은 더 최근 새로고침의 작업 중 상태를 해제하면 안 된다.
- **FR-003**: 오래된 새로고침은 최신 커밋 선택의 내용과 진행 상태를 변경하면 안 된다.
- **FR-004**: 성공과 실패 모두 상태를 정리하고 변경된 상태를 화면에 반영해야 한다.
- **FR-005**: 완료 순서가 다른 회귀 시나리오를 자동 검증해야 한다.

### 주요 개체

- 저장소 탭: 선택한 커밋, 진행 중 조회와 조회 결과를 보유한다.
- 새로고침 요청: 자신의 완료 상태만 정리할 수 있는 조회 작업이다.

## 성공 기준

- **SC-001**: 두 조회의 완료 순서 두 가지 모두 재시작 없이 작업 중 차단이 해제된다.
- **SC-002**: 연속 새로고침의 완료 순서 두 가지 모두 최신 요청의 상태와 결과가 보존된다.
- **SC-003**: 성공·실패와 오래된 결과 처리의 자동 회귀 검증이 모두 통과한다.

## 가정

- 범위는 확인된 조회 상태 소유권 결함과 같은 상태 전이 경로 점검이다. 외부 프로세스의 무기한 대기나 모든 기능의 재설계는 포함하지 않는다.
- 실제 진행 중인 작업의 기존 차단 정책과 단축키 설정을 유지한다.
- 명확화 검토 결과 기능 범위, 실패 처리, 완료 기준에 추가 사용자 결정이 필요한 모호함은 없다.
