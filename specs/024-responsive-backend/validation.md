# 구현 및 검증 결과

## 목적과 최종 동작

선택·표시 상태 갱신은 UI 스레드에 남기고 저장소·변경 파일·참조·설정 I/O와 Git 그래프 준비는 공통 백그라운드 실행 경로로 분리했다. 커밋 행 선택 시 히스토리·커밋상세는 즉시 선택되고 파일 조회 완료를 기다리지 않는다. 요청 번호·프로젝트·커밋·패널 모드·참조 이름을 확인해 이전 성공과 오류를 버린다.
일반 조회에 로딩 표시를 추가하지 않았다. diff 뷰어의 조회 중 문구는 제거했고 결과 대기 중 빈 목록 안내도 숨겼다. 기존 시작 전용 새/깃털 화면과 저장소 대화상자는 유지한다. 이전 파일을 새 커밋의 파일로 오인해 조작하지 못하도록 선택과 파일 목록을 무효화하며, 오래된 파일 행 이벤트도 패널 버전으로 거절한다.

## 주요 변경 파일

- src/workspace_backend.rs: 패널/참조 요청·결과와 실제 조회, 초기 복원 데이터, 파일 목록 변환, 직렬 세션 작성기·최신 대기값 병합·종료 배출 및 작성기 테스트.
- src/ui.rs: 순수 상태 전이·요청 큐·비동기 제출·최신성 검증·결과 반영. 비활성 프로젝트 변경은 캐시 무효화 후 재선택 시 갱신한다.
- src/diff_viewer.rs: 단축키 초기 읽기·저장 비동기화와 설정 버전·편집 폼 검증. 기존 diff 세대 검사는 유지한다.
- src/history.rs: Send 가능한 PreparedHistory와 UI 핸들 생성 분리.
- src/session.rs: 정규화된 경로의 순수 최근 목록 갱신 추가. 기존 정규화 API와 저장 형식은 유지한다.
- src/backend.rs: 공통 spawn과 테스트용 스레드 지역 정책 주입. 기존 지연 옵션·게이트웨이 유지.
- src/main.rs: 앱 이벤트 루프 반환 후 공유 세션 작성기를 배출해 마지막 변경을 보존한다.
- .specify/feature.json 및 specs/024-responsive-backend/: 명세·계획·작업·계약·검증 문서.

## 구조 및 안전성

UI 핸들러는 요청 생성만 수행하고 렌더링 시작 시 공통 실행기가 대기 요청을 제출한다. Window·Context·Rc를 작업 스레드로 전달하지 않는다. 완료 콜백은 소유 결과만 적용한다. 기록 그래프 준비는 작업 스레드에서 수행하고 UI에서는 목록·스크롤 핸들만 구성한다.
패널/참조의 오래된 응답은 선택·파일·오류·스크롤을 변경하지 않는다. 무효 프로젝트/닫기 이벤트가 현재 유효 요청을 취소하지 않도록 유효성 검사 뒤 요청을 무효화한다. 파일 변경 후에는 경로와 staged 식별자로 기존 선택을 복원한다.
세션 작성기는 한 번에 하나만 파일을 쓰고 최신 대기 스냅샷 하나만 유지한다. UI는 파일 쓰기를 기다리지 않는다. 요청 번호가 이전인 저장 오류는 최신 상태를 덮지 않는다. 단축키도 초기 읽기와 저장의 버전을 검사하며 저장 도중 편집·폼 닫기·기본값 복원이 있었다면 기존 완료가 최근 편집 폼을 닫지 않는다.

## 자동 검증

- 명세·명확화·구현 전 분석: 요구사항 9개가 구현·검증 작업에 연결되며 미해결 질문·누락·충돌 없음.
- 기존 테스트는 실제 요청을 별도 스레드에서 완료하고 운영 코드와 같은 결과 적용 함수를 사용하도록 테스트 구동기를 추가했다. 운영 코드에 테스트용 동기 실행 분기는 넣지 않았다.
- 지연된 요청이 대기 중일 때 커밋 선택이 즉시 반환하고 UI 스레드의 백엔드 게이트웨이 호출이 0건인지 확인했다.
- 패널 역순 완료·늦은 오류·프로젝트/파일 모드/시작 탭 전환·프로젝트 닫기·무효 이벤트를 검증했다.
- 참조 선택 후 늦은 성공·실패가 새 커밋/참조를 덮지 않는지 확인했다. 기존 오래된 태그 확장·선택 강조·스크롤 유지 검증도 통과했다. 초기에 드러난 비동기 참조 선택 강조 누락은 기존 테스트 조건을 유지한 채 수정했다.
- 세션 작성기의 다른 스레드 실행·비차단 제출·직렬 처리·최신 대기값 병합·결과 수신자 소멸 후 저장·오류/패닉 복구·flush를 검증했다.
- 단축키 초기 읽기 실패·기본값 유지·중복 저장 차단·이전 초기 읽기/저장 결과 거절·실패 후 재시도를 검증했다.
- 최종 cargo test --offline --quiet: 153개 통과, 실패 0개, 기존 수동 성능 테스트 2개 제외.
- cargo fmt --check, cargo check --offline, cargo clippy --offline --all-targets, cargo build --offline: 통과. 마지막 소스 수정 후 전체 테스트·정적 검사·Clippy·기본 빌드를 재확인했다.

## 실제 GPUI 이벤트 루프 실행 검증

제품 코드의 별도 사본을 target/responsiveness-check에 만들고, 실제 src 모듈을 그대로 사용하면서 다음 프레임 콜백에서 선택 요청·프레임 집계·자동 창 닫기만 주입했다. 제품용 진단 옵션이나 테스트 코드 분기를 추가하지 않았다. 테스트 저장소와 LOCALAPPDATA는 작업 공간 안의 격리 경로를 사용했다.

- 백엔드 지연 250ms: 종료 코드 0, 240프레임, 커밋 선택 8회, 백그라운드 호출 18회, UI 스레드 동기 호출 0회, 정상 종료 마커 확인.
- 백엔드 지연 1500ms: 종료 코드 0, 1200프레임, 커밋 선택 33회, 저장 요청 9회, 백그라운드 호출 69회, UI 스레드 동기 호출 0회. 마지막 저장 배출 후 정상 종료 마커를 확인했다. 전체 실행 시간은 약 10.26초였다.
- 프로그램 방식으로 프로젝트 재선택·시작 탭 열기/닫기·참조 선택·세션 저장도 수행했다. 지연 중 화면 갱신과 선택 요청 처리가 계속됐으며 검증 종료 후 잔류 앱 프로세스가 없었다.
- 최초 임시 검증기는 렌더링 컨텍스트 밖에서 request_animation_frame을 호출해 GPUI 단언에 실패했다. 검증기만 window.refresh로 수정한 뒤 위 검증을 통과했다. 제품 코드의 오류나 남은 실패가 아니다.

## 남은 제약 및 미검증

실제 마우스로 창·행·단축키 폼을 조작하는 수동 검증과 모든 저장소 규모에 대한 프레임 시간 측정은 수행하지 않았다. 위 실행 검증은 실제 GPUI 창과 자동 이벤트 요청을 사용한 것으로 수동 시각 검증과 구분한다.
오래된 백엔드 작업 자체를 강제로 취소하지는 않으며 결과만 폐기한다. 대규모 저장소에서 실제 Git I/O 완료 시간은 저장소에 따라 달라질 수 있다. 정상 종료 시 마지막 설정 저장을 끝내기 위해 창이 닫힌 뒤 프로세스가 잠시 대기할 수 있으며, UI 이벤트 루프가 실행 중일 때는 기다리지 않는다. 강제 프로세스 종료에서는 저장 완료를 보장하지 않는다.
기존 GPUI 실수 리터럴·향후 호환성·미사용 commit_files 경고와 기존 중첩 조건 Clippy 경고가 남아 있다. 기존 remember API는 호환성을 위해 보존되어 운영 빌드에서 미사용 경고가 표시될 수 있다. 사용자 설정·저장소 및 작업 중 추가된 README.md는 변경하지 않았다.

## 히스토리 조회의 100ms 지연 안내 추가

### 변경 목적과 결과

추가 요구에 따라 변경 파일 패널의 히스토리 파일 조회가 느릴 때만 목록 영역에 정확히 ‘조회 중 입니다..’를 표시한다. 기존 고정 커밋상세 행·비동기 처리·최신 응답 검사·작업 트리·다른 패널의 표시 정책은 유지한다. 스피너나 오버레이는 추가하지 않았다.
공통 src/loading.rs의 공개 LOADING_DELAY를 Duration::from_millis(100)으로 정의했다. 이후 다른 화면에서도 같은 지연값과 DelayedLoading 상태를 사용할 수 있다. 실행 옵션이나 사용자 설정 파일 형식은 추가하지 않았다.

### 주요 변경 파일

- src/loading.rs: 공통 지연 상수, 요청 번호·시작 시각 기반 지연 표시 상태, 결정적 시각 경계 테스트.
- src/main.rs: loading 모듈 등록.
- src/ui.rs: 히스토리 요청 시작 시각·비차단 타이머·백엔드 응답 완료 AtomicBool·표시 조건·완료/무효화 해제·목록 문구·회귀 테스트.
- specs/024-responsive-backend/: 추가 요구사항·명확화·계획·작업·계약·검증 갱신.

### 동작 및 안전성

히스토리 요청 시작부터 공통 지연 시간의 남은 값만 GPUI 타이머로 기다린다. 타이머는 UI를 차단하지 않으며 현재 요청 번호·진행 중 상태·히스토리 모드·활성 프로젝트 화면을 검사한다. 백엔드 작업 완료 플래그도 확인해 응답이 이미 왔는데 UI 반영만 지연된 경우에는 문구를 새로 켜지 않는다.
성공·오류 반영 시 지연 표시를 초기화한다. 다른 커밋·프로젝트·작업 트리·시작 탭으로 전환하거나 프로젝트를 닫을 때도 초기화한다. 오래된 타이머나 이전 응답은 최신 요청의 표시 상태를 변경하지 않는다. 빠른 응답의 깜빡임을 막으며 응답 완료를 인위적으로 늦추지 않는다.

### 검증 결과

- 명세·명확화·구현 전 일관성 분석: 추가 요구사항 2개와 성공 기준을 구현·검증 작업에 연결했다. 즉시 로딩 표시 제외 정책의 예외를 히스토리 목록의 지연 안내로 명확히 했다. 미해결 질문·누락·충돌 없음.
- 공통 상태 테스트: 99ms 미표시·100ms 표시, 잔여 지연 계산, 중복 알림 억제, 완료와 새 요청의 이전 타이머 무효화를 검증했다.
- UI 상태 테스트: 느린 응답 표시·성공 후 해제·백엔드 응답 완료 후 UI 반영 전 미표시, 이전 타이머/응답 무시, 오류 후 해제, 작업 트리·시작 탭·다른 프로젝트·닫기 전환을 검증했다.
- cargo test --offline --quiet: 158개 통과, 실패 0개, 기존 수동 성능 테스트 2개 제외.
- cargo fmt --check, cargo check --offline, cargo clippy --offline --all-targets: 통과.
- cargo build --offline: 현재 사용 중인 기본 target/debug/feather-git.exe 교체에서 접근 거부로 실패했다. 실행 중인 사용자 앱(PID 44612)은 종료하지 않았다.
- cargo rustc --offline --bin feather-git -- --emit=link=target/debug/feather-git-loading-verified.exe: 별도 실행 파일 컴파일·링크 성공.

### 실제 GPUI 타이머 실행 검증

동일한 제품 컴포넌트를 사용하는 임시 검증 앱을 target/history-loading-check에 만들고, 다음 프레임 콜백에서 커밋 선택·표시 상태 관찰·자동 창 닫기만 주입했다. 실제 src 모듈을 그대로 사용했고 제품 코드에는 테스트 분기나 진단 옵션을 추가하지 않았다. 설정과 저장소는 작업 공간 안의 격리된 테스트 경로를 사용했다.

- 백엔드 지연 250ms: 종료 코드 0, 선택 후 약 105ms에 지연 표시 상태가 켜짐. 응답 완료 후 표시가 꺼짐. UI 스레드 동기 호출 0건, 정상 종료 마커 확인.
- 백엔드 지연 0ms: 종료 코드 0, 빠른 응답에서는 지연 표시 상태가 한 번도 켜지지 않음. 완료 후 미표시, UI 스레드 동기 호출 0건, 정상 종료 마커 확인.

### 제약 및 미검증

마우스를 직접 조작해 실제 문구의 외형을 보는 수동 시각 검증은 수행하지 않았다. 자동 GPUI 검증은 실제 이벤트 루프의 타이머·표시 상태·완료 해제를 확인한다. 정확한 화면 표시 시점은 100ms 이후 다음 UI 프레임이므로 기기와 프레임 일정에 따라 약간 늦을 수 있다.
기본 실행 파일을 최신 코드로 바꾸려면 실행 중인 앱을 닫고 다시 빌드해야 한다. 기존 의존성·미사용 호환 함수·중첩 조건 Clippy 경고는 유지한다.

### 지연 안내 추가 후 수렴 검사

요구사항 11개·성공 기준 5개·수용 시나리오 15개와 공통 지연값·시작 시각·비차단 타이머·백엔드 완료 플래그·요청 버전·목록 한정 표시·완료/오류/전환 해제를 실제 코드·자동 테스트·GPUI 실행 결과에 대조했다. 누락·부분 충족·모순·요청 외 구현은 0개이며 후속 구현 작업은 없다. 미작성 헌장 템플릿의 규범 검사는 생략했다. tasks.md는 수렴 검사 중 변경하지 않았다. 기본 파일 잠금과 직접 문구 외형 확인은 위 제약/미검증 항목으로 구분한다.

## 2026-11-14 로딩 안내 150ms 변경 검증

- 명세·명확화·계획·작업·일관성 분석 후 src/loading.rs의 공통 상수를 150ms로 변경했다. 백엔드 지연과 다른 타이머는 변경하지 않았다. 기존 완료 작업의 100ms 기록은 당시 이력으로 유지한다.
- 기존 경계 테스트를 149ms 미표시·150ms 표시·잔여 1ms로 먼저 변경하여 기존 100ms 상수에서 실패함을 확인했다. 상수 변경 후 전체 테스트는 164개 통과, 실패 0개, 기존 수동 성능 측정 무시 2개다.
- cargo fmt --check, cargo check --offline, cargo clippy --offline --all-targets는 성공했다. 기존 코드·의존성 경고만 남았다.
- cargo build --offline는 컴파일·링크 후 target/debug/feather-git.exe를 교체하는 단계에서 접근 거부(os error 5)로 실패했다. 해당 경로의 앱이 실행 중임을 확인했으며 앱을 강제 종료하지 않았다. 실행 파일 갱신은 잠금 해제 후 재시도가 필요하다.
- 수렴 점검에서 150ms 요구사항과 구현의 차이는 없지만 빌드 검증 미완료를 발견하여 T021을 추가했다. T019는 완료 표시하지 않았다. GUI 직접 확인은 수행하지 않았다.
