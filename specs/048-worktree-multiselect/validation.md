# 검증 결과

## 워크플로우와 일관성

명세·명확화·계획·작업·일관성 분석·구현·수렴을 수행했다. 명확화 질문 2개와 답변을 명세에 반영했다. Space는 선택 파일 전체, 중복 경로는 Stage 우선이다. 명세 품질 점검 5/5 통과다. FR-001~002는 T003~005, FR-003~004는 T006~007, FR-005~006은 T008~010, FR-007은 관련 통합 작업에 대응한다. Constitution은 미작성 템플릿이며 확장 훅은 없다.

## 구현 결과

- src/virtual_list.rs: 기존 단일 목록을 어댑터로 유지하면서 다중 강조·수정키 이벤트 API와 MultiSelection을 추가했다. 일반 클릭·Shift 범위·Ctrl 토글·Ctrl+Shift 추가 범위·역방향·빈 선택·복원을 지원한다.
- src/ui.rs: 작업 트리에서만 다중 선택을 적용하고 커밋 기록 파일은 기존 단일 선택을 유지한다. 여러 선택은 현재 목록 순서의 Files 대상이다. 재조회 시 경로·Stage 상태 집합으로 선택을 복원한다.
- src/diff_viewer.rs: 기존 파일 뷰어를 파일별 자식으로 재사용하고 파일명·Stage 상태를 구분해 세로 나열한다. 각 파일의 조회 세대·본문 선택·체크·Stage·충돌·공백 장식·스크롤·로딩·오류를 분리한다. 같은 파일 자식은 재사용하고 선택에서 빠진 쓰기 중 자식은 완료까지 유지한다. 이벤트·관찰·하단 안내·busy·차단 상태를 연결했다.
- src/virtual_list.rs·src/diff_viewer.rs: 자식 스크롤 경계에서는 부모가 이어받고, 실제 content mask 밖의 자식은 클릭·휠을 받지 않는다. 원래 좌표는 유지해 텍스트 행 인덱스를 바꾸지 않는다.
- src/workspace_backend.rs·src/ui.rs: 배치 토글은 경로별로 한 번 처리하며 미스테이지가 선택되면 Stage를 우선한다. 기존 파일별 인덱스 잠금과 stale 검사를 재사용한다. 성공 건수·실패 파일을 안내하고 성공·실패별 식별자를 복원한다. 그래프 없는 파일 갱신을 유지한다.

## 자동 검증

- cargo check --offline: 통과.
- cargo fmt --check: 통과.
- cargo test --offline: 최종 248개 통과, 실패 0개, 기존 3개 제외. 제외 항목은 성능 측정용 2개와 명시적 외부 저장소 검증 1개다.
- 새 테스트 5개: 선택 모델의 모든 수정키·범위·해제·복원 경계, Workspace의 다중 대상·stale 이벤트·재정렬 후 식별자 복원·커밋 기록 단일 모드, 다중 대상의 순서·Stage·저장소별 구분, 실제 저장소의 배치 Stage/Unstage·중복 경로 우선·부분 실패·원문 보존, 잘린 뷰포트의 입력 차단과 원래 좌표 유지.
- 배치 테스트의 최초 임시 경로는 libgit2 접근 권한 오류가 발생했다. 기존 저장소 테스트 방식과 같이 target/batch-stage-tests 아래로 fixture 위치를 옮겼으며 기능 단언은 유지했다. 이후 개별 및 전체 테스트가 통과했다.
- cargo clippy --offline --all-targets: 통과. 기존 미사용 코드·중첩 조건·의존성 경고는 남아 있다.
- cargo build --offline: 컴파일·링크 후 target/debug/feather-git.exe 교체에서 액세스 거부로 실패했다. 실행 파일 잠금으로 보이며 기존 앱은 종료하지 않았다. 테스트 실행 파일의 컴파일·링크·실행은 성공했다.

## 수렴 보완

최초 수렴에서 선택에서 빠진 쓰기 중 자식의 실패 메시지 보존을 보완 항목으로 확인해 T013을 추가했다. 기존 notify 관찰과 별개로 정확한 쓰기 실패 이벤트를 전달하여 숨겨진 자식의 파일명 포함 오류를 부모에 보존하고 다중 화면에도 표시하도록 구현했다. 보완 후 전체 248개 테스트와 서식·Clippy를 다시 실행해 통과했다.

최종 FR-001~007, SC-001~002, 세 사용자 이야기와 선택·파일 경계·배치·상태 복원·수명·오류 전달을 코드와 테스트로 대조했다. 미구현·부분 구현·상충·범위 밖 추가 항목은 0건이며 추가 구현 작업은 없다.

## 실제 화면 검증 제한

computer-use 스킬로 실행 중 창을 조회한 후 앱 상태를 읽으려 했으나 자동 승인 검토가 feather-git 앱 사용이 승인되지 않았다는 이유로 거부했다. 앱을 닫거나 재실행하지 않았다. 실제 Shift·Ctrl 입력, 여러 파일 배치·중첩 스크롤·자식 포커스·쓰기 중 탐색·오류 전달의 화면 동작은 미검증이다. 구독·수명 경로는 코드로 확인했으며 이를 GUI 자동 검증 완료로 주장하지 않는다. 현재 실행 파일 교체도 미완료다.

## 후속 요청: 다중 선택 헤더 단순화

speckit-specify로 기존 FR-003과 수용 기준을 갱신하고 speckit-clarify에서 추가 질문이 필요한 모호성이 없음을 확인했다. speckit-plan과 speckit-tasks로 호출 흐름·표시 범위·검증 및 T014~T016을 정의했다. speckit-analyze에서 요구사항/계획/작업 간 누락·모순·중복은 없었다. 확장 훅 설정은 없다. Constitution은 미작성 템플릿으로 적용할 구체 원칙이 없다.

speckit-implement: src/diff_viewer.rs의 다중 파일 상태 행을 제거하고 자식 뷰어에만 hide_header를 지정했다. 최상위 뷰어의 기본값은 false여서 단일 선택 경로 헤더와 커밋상세 헤더는 유지한다. 다중 선택 상단은 활성 선택 수를 사용하는 선택한 파일 N개만 표시한다. 본문·제어·오류·쓰기 대상은 유지한다.

- cargo fmt --check: 통과.
- cargo test --offline: 248개 통과, 실패 0개, 기존 3개 제외.
- cargo clippy --offline --all-targets: 통과. 기존 경고만 존재한다.
- cargo build --offline: 컴파일·링크 후 실행 중 target/debug/feather-git.exe 제거가 액세스 거부(os error 5)로 실패했다. 실행 파일 교체 및 실행 중 앱 반영은 미완료다.
- 실제 GUI 화면 확인은 수행하지 않았다. 표시 분기와 자식 생성·재사용 경로는 코드로 확인했다.

speckit-converge: 변경된 FR-003의 다중 개수 헤더·경로/상태 헤더 숨김·단일 선택 헤더 보존과 FR-004/007의 기존 본문/조작 보존을 대조했다. 관련 계획 결정과 T014~T016이 구현 및 검증 결과와 일치한다. 미해결 구현 차이와 추가 작업은 없다. GUI 검증과 실행 파일 교체 한계는 위에 명시했다.

## 후속 요청: 헤더 디자인 통일

speckit-specify로 FR-008과 수용 기준을 추가하고 speckit-clarify에서 기존 파일명 헤더를 비교 기준으로 확정하여 질문이 불필요함을 확인했다. speckit-plan으로 두 렌더 경로와 스타일 차이를 분석하고 speckit-tasks로 T017~T019를 정의했다. speckit-analyze에서 누락·모순·중복은 없었다. 확장 훅은 없으며 Constitution은 미작성 템플릿이다.

speckit-implement에서 src/diff_viewer.rs의 개수 헤더를 36px 높이·px_5 여백·세로 중앙 정렬·SEMIBOLD 제목·LINE 색상 하단 1px 선으로 맞췄다. 제목의 축소/말줄임 속성도 파일명 헤더와 동일하게 적용했다. 선택 개수와 자식 헤더 숨김 및 본문 동작은 유지한다.

- cargo fmt --check: 통과.
- cargo clippy --offline --all-targets: 통과. 기존 경고만 존재한다.
- cargo build --offline: 컴파일·링크 후 실행 중 feather-git.exe 제거가 액세스 거부(os error 5)로 실패했다. 실행 중 앱 반영은 미완료다.
- 이번 변경은 표시 속성만 수정하므로 자동 테스트를 추가하거나 전체 테스트를 반복하지 않았다. 직전 변경의 전체 테스트 결과는 248개 통과·3개 제외다.
- 실제 화면의 외형은 미검증이다.

speckit-converge에서 FR-008과 수용 기준, 계획의 스타일 항목 및 T017~T019를 코드와 대조했다. 높이·여백·정렬·굵기·하단 선과 제목 말줄임이 기존 파일명 헤더와 같고 개수 표시 정책도 유지된다. 미해결 구현 차이는 없으며 추가 작업을 생성하지 않았다. GUI 및 실행 파일 교체의 검증 제한은 위에 기록했다.
