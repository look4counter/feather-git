# 구현 및 검증 결과

## 단계별 결과

speckit-specify로 실제 파일 행 트리거와 모든 탭의 공통 메뉴를 명세했다. speckit-clarify에서 사용자 답변인 열기/탐색기는 클릭 파일 하나, 복사는 선택 전체를 반영했다. 우클릭은 선택을 유지하고 커밋 기록도 현재 작업 디렉터리 경로를 사용한다고 정의했다. speckit-plan으로 파일 행/상세 오프셋/선택/기존 메뉴·키 처리와 GPUI OS API를 분석했다. speckit-tasks로 경로 준비→행 연결→동작/키 검증→회귀 순서를 정의했다. speckit-analyze에서 명세·계획·작업 사이의 누락·모순·중복은 없었다. 확장 훅 설정은 없고 Constitution은 미작성 템플릿이다.

## 주요 변경 파일

- src/ui.rs: 파일 행 콘텐츠에만 우클릭 핸들러를 추가하고 패널 전체 핸들러를 제거했다. FileMenuRequest로 프로젝트/세대/탭/행을 검증하고 커밋상세와 잘못된 이벤트를 거부한다. 두 탭에서 열기·탐색기에서 보기·경로복사 / Ctrl + Shift + C 메뉴를 구성하고 작업 트리에만 기존 Stage/폐기를 유지한다. 클릭 파일과 현재 선택 집합을 분리하며 선택은 바꾸지 않는다. 복사는 선택 전체의 원본 경로를 절대경로로 만들어 순서대로 중복 제거하고 줄바꿈으로 복사한다. 파일 패널 포커스의 단축키도 같은 복사 경로를 사용한다. OS 준비 결과의 문맥을 재검증하고 GPUI open_with_system/reveal_path를 호출한다.
- src/path_display.rs: 존재 여부 조회 없이 저장소 절대경로와 원본 Git 상대경로를 결합하고 경로 이탈/잘못된 입력을 거부하는 함수를 추가했다. 기존 Windows 표시 경로 정리를 재사용한다.
- src/workspace_backend.rs: 작업 스레드에서 OS 대상의 존재 여부를 확인한다. 누락 파일의 열기는 오류로 알리고 탐색기는 가장 가까운 기존 상위 폴더를 열도록 준비한다. Git 조회/쓰기를 추가하지 않는다.
- src/context_menu.rs: 기존 공통 단축키 매칭 테스트에 Ctrl+Shift+C 조합을 보강했다.

## 자동 검증

- 행 메뉴 상태 테스트에서 클릭 파일 하나와 선택 경로 집합이 다름을 확인하고 중복 상태 행의 경로 한 번 복사·선택 보존·빈 선택·두 탭·커밋상세 오프셋·범위 밖·오래된 프로젝트/세대/탭·조회/쓰기 중 거부를 검증했다.
- Ctrl+Shift+C만 복사 조합으로 인식하고 Ctrl+C·추가 수정키·다른 키는 거부함을 검증했다. 메뉴 배지 키 매칭도 확인했다.
- 한글/공백/패턴 문자 경로 결합과 상대 루트/상위 탈출/빈 경로 거부를 검증했다.
- 실제 임시 파일로 열기/탐색기 대상의 정확한 경로와 누락 파일 오류/상위 폴더 fallback을 검증했다. OS 앱을 실제 실행하지 않았다.
- 파일 관련 테스트 23개 통과 후 전체 cargo test --offline: 263개 통과, 실패 0개, 기존 3개 제외.
- cargo fmt --check: 통과.
- cargo clippy --offline --all-targets: 통과, 기존 경고만 존재한다.
- cargo build --offline: 컴파일·링크 후 실행 중 target/debug/feather-git.exe 제거가 액세스 거부(os error 5)로 실패했다. 현재 실행 파일 교체는 미완료다.

## 검증 한계

실제 화면의 우클릭 위치/메뉴 외형·OS 기본 앱/탐색기 실행·클립보드 내용은 직접 검증하지 못했다. 코드와 순수 상태/파일 준비 테스트로 확인했으며 GUI 통합 검증 완료로 주장하지 않는다. GPUI OS 실행 API는 결과를 반환하지 않아 실행 단계 오류는 기존 플랫폼 로그에 기록된다. 준비 단계 오류는 알림 팝업으로 표시한다. 현재 실행 중 앱에는 반영되지 않았다.

## 수렴 점검

speckit-converge에서 FR-001~006과 SC-001~002 및 세 사용자 이야기의 행 경계/공통 메뉴/클릭·선택 분리 수용 기준을 코드와 테스트에 대조했다. 패널 전체 Right 핸들러는 없고 실제 파일 행에만 연결되며 커밋상세는 별도 행으로 제외된다. OS 대상 준비는 작업 스레드이고 콜백은 문맥을 재검증한다. 경로복사와 메뉴/패널 단축키는 같은 선택 경로 메서드를 사용하며 다른 Git 갱신을 추가하지 않는다. T001~T005와 계획의 기존 플랫폼/선택 재사용이 구현 및 자동 검증과 일치한다. 미해결 구현 차이와 추가 작업은 없고 수렴 단계에서 tasks.md를 수정하지 않았다. GUI·OS 통합·실행 파일 교체 제한은 위에 별도로 기록했다.

## 후속 탐색기 및 메뉴 열 수정 검증

speckit-specify로 FR-003을 부모 폴더 열기로 구체화하고 FR-007의 이름/단축키 비중첩 기준을 추가했다. speckit-clarify에서 파일 선택용 COM 경로 대신 요청에 맞는 폴더 열기를 사용하고 기존 파일 선택은 유지함을 명확히 했다. speckit-plan에서 Windows reveal_path의 작업 스레드 Shell COM 호출/로그 전용 실패와 확장 경로 전달, 메뉴 flex 최소 너비/축소를 분석했다. speckit-tasks로 T006~T009를 정의했고 speckit-analyze에서 명세·계획·작업의 누락/모순은 없었다. 실제 실패 HRESULT는 수집하지 못했으므로 특정 COM 오류를 원인으로 확정하지 않는다.

speckit-implement로 src/workspace_backend.rs의 탐색기 준비가 기존 파일도 항상 부모 폴더를 반환하도록 변경하고 불필요한 결과 reveal 플래그를 제거했다. src/ui.rs는 기존 display_path로 Shell 호출 시 Windows 확장 드라이브/UNC 접두사만 정리한 후 open_with_system으로 폴더를 직접 연다. 원본 파일시스템 조회 경로는 유지한다. 파일 기본 앱 열기도 Shell 경계의 정리 경로를 사용한다.

src/context_menu.rs는 너비를 360px로 확보하고 이름의 min_w_0/truncate 및 단축키의 flex_shrink_0/whitespace_nowrap을 적용했다. 이름은 자신에게 할당된 영역 안에서 말줄임되고 단축키는 축소/줄바꿈되지 않는다. 단순 스타일을 복제하는 테스트는 추가하지 않았다.

- 기존 파일의 탐색기 대상이 부모 폴더여야 한다는 기대값으로 수정 전 실패를 재현했다. 이는 실제 Windows Explorer 실행 실패의 GUI 재현이 아니라 목표 경로 계약의 재현이다.
- 수정 후 OS 대상 준비 테스트 1개와 드라이브/UNC 접두사·경로 보존 테스트 5개가 통과했다.
- 최종 cargo test --offline: 263개 통과, 실패 0개, 기존 3개 제외.
- cargo fmt --check 및 cargo clippy --offline --all-targets: 통과, 기존 경고만 존재한다.
- cargo build --offline: 컴파일·링크 후 실행 중 feather-git.exe 제거가 액세스 거부(os error 5)로 실패했다. 현재 실행 파일 교체는 미완료다.
- 실제 Explorer 창 실행과 메뉴 외형/긴 글자 겹침의 GUI 확인은 수행하지 못했다. UI 스타일/호출 경로는 코드로 확인했으며 실제 GUI 성공으로 주장하지 않는다.

speckit-converge에서 갱신 FR-003과 FR-007의 폴더 열기/확장 경로 정리/이름·단축키 영역 분리, 기존 FR-002/004~006의 파일 열기·복사·문맥/쓰기 보호 및 T006~T009를 코드와 대조했다. 부모 폴더 준비와 OS 열기 경로가 일치하며 메뉴 이름 최소 너비/말줄임과 단축키 축소 금지가 적용됐다. 미해결 구현 차이와 추가 작업은 없다. 수렴 단계에서 tasks.md는 수정하지 않았으며 실제 GUI 및 실행 파일 교체 한계는 별도 기록했다.

## 후속 구분선 검증

speckit-specify로 FR-008을 추가하고 speckit-clarify에서 경로복사 뒤에 다른 항목이 있을 때만 장식 선을 그리며 동작/탐색은 유지함을 명확히 했다. speckit-plan은 MenuItem 인덱스를 보존하는 장식 옵션을 설계했고 speckit-tasks로 T010~T012를 정의했다. speckit-analyze에서 문서/작업의 모순·누락은 없었다. speckit-implement로 src/context_menu.rs의 separator_after 옵션과 비상호작용 장식 선을 추가하고 src/ui.rs의 경로복사 항목에 지정했다. 작업 트리는 뒤에 Stage/폐기가 있어 선이 표시되고 커밋 기록에서는 마지막 항목이라 끝 선을 생략한다.

cargo fmt --check와 cargo clippy --offline --all-targets가 통과했다. 기존 메뉴 탐색·단축키 매칭 테스트 2개도 통과했다. 단순 장식 변경이므로 전체 테스트와 배포 실행 파일 빌드는 반복하지 않았다. 실제 화면과 실행 중 앱 교체는 수행하지 않았다.

speckit-converge에서 FR-008의 위치·후속 항목 조건·비실행 장식·기존 탐색 보존과 T010~T012를 코드에 대조했다. 명세와 구현이 일치하며 미해결 차이/추가 작업은 없다. 수렴 단계에서 tasks.md는 수정하지 않았다.

## 후속 우클릭 선택 및 헤더 집계

speckit-specify로 FR-009/010을 추가하고 이전 선택 유지 정책을 최신 사용자 지시로 갱신했다. speckit-clarify에서 미선택 행은 단일 선택, 기존 선택 행은 다중 유지, 현재 표시 행 단위 전체/M/D/A 집계와 작업 트리 Staged 별도 표시를 정의했다. speckit-plan으로 메뉴 구성 전 선택 갱신, 기존 상세 오프셋/일반 클릭 재사용 및 S· 접두사 기반 집계를 설계했고 speckit-tasks로 T013~T015를 정의했다. speckit-analyze에서 명세·계획·작업의 누락/모순은 없었다. 파일 이력 명세의 공통 메뉴 선택 정책도 같은 조건으로 갱신했다.

speckit-implement로 src/ui.rs의 prepare_file_menu_selection을 메뉴 구성 전에 호출한다. 미선택 행은 기본 수정키의 기존 선택 API로 단일 선택하고, 이미 선택된 행은 변경하지 않는다. 커밋상세/오래된 프로젝트·세대·탭/조회·쓰기·모달 가드는 유지한다. 선택 갱신 후 메뉴의 복사/Stage/폐기 활성 조건과 대상을 계산한다. 선택 변경 자체로 파일 목록/저장소를 재조회하지 않는다.

FileCounts는 표시 행의 S· 접두사를 분리하여 Staged와 M/D/A를 집계한다. 전체는 기존 파일 행 수이며 같은 경로의 두 상태 행은 각각 집계한다. U/R 등 다른 상태는 전체에만 포함한다. files_heading은 전체·Staged·M·D·A 배지를 표시하고 커밋 기록에서는 Staged만 생략한다. 좁은 패널에서 배지가 겹치지 않도록 줄바꿈과 최소 높이를 사용한다.

- 새 우클릭 테스트: 미선택 단일 선택·기존 다중 유지·같은 행 무변경·빈 선택·오래된 문맥·커밋상세 제외/오프셋·조회 중 거부·재조회 미발생을 확인했다.
- 새 집계 테스트: Staged 접두사·중복 경로·M/D/A·기타 상태·빈 목록·커밋 기록 원본을 확인했다.
- 최종 cargo test --offline: 269개 통과, 실패 0개, 기존 3개 제외.
- cargo fmt --check 및 cargo clippy --offline --all-targets: 통과, 기존 경고만 존재한다.
- cargo build --offline: 컴파일·링크 후 실행 중 feather-git.exe 제거가 액세스 거부(os error 5)로 실패했다. 이번 실행 파일 교체는 미완료다.
- 실제 GUI의 우클릭/배지 줄바꿈·외형은 직접 확인하지 못했다. 코드/상태 테스트로 검증했으며 실제 화면 검증 완료로 주장하지 않는다.

speckit-converge에서 FR-009/010과 기존 FR-001/004/005의 행 경계·선택 대상·메뉴 보호, T013~T015를 코드에 대조했다. 메뉴 전에만 미선택 행을 선택하고 기존 다중 집합은 유지하며 집계는 현재 탭의 표시 행과 일치한다. 작업 트리 Staged 표시와 커밋 기록 생략, 좁은 패널 배지 줄바꿈이 계획과 일치한다. 미해결 구현 차이와 추가 작업은 없으며 수렴 단계에서 tasks.md는 수정하지 않았다. GUI와 실행 파일 잠금 한계는 별도 기록했다.

## 후속 개수 표시 원복 검증

speckit-specify로 FR-010을 전체 개수만 표시하도록 원복하고 speckit-clarify에서 세부 배지/집계만 제거하며 우클릭 선택은 유지함을 명확히 했다. speckit-plan으로 FileCounts/files_heading과 선택 처리의 독립성을 분석하고 speckit-tasks로 T016~T018을 정의했다. speckit-analyze에서 최신 요구와 문서/작업의 충돌·누락은 없었다. speckit-implement로 src/ui.rs에서 FileCounts/files_heading 및 취소된 세부 집계 전용 테스트를 제거하고 기존 heading(변경 파일, files.len())을 복구했다. 사용자 원복에 따른 전용 테스트 제거이며 실패 회피나 기존 우클릭 테스트 삭제가 아니다.

cargo fmt --check와 cargo clippy --offline --all-targets가 통과했고 기존 우클릭 선택 회귀 테스트 1개도 통과했다. 전체 테스트와 배포 실행 파일 빌드는 반복하지 않았다. 실제 화면 확인과 실행 중 앱 교체는 수행하지 않았다.

speckit-converge에서 최신 FR-010과 기존 FR-009 및 T016~T018을 코드에 대조했다. 헤더는 기존 공통 전체 개수 표시이며 세부 집계는 없고 우클릭 선택/다중 유지 코드는 보존됐다. 미해결 구현 차이와 추가 작업은 없으며 수렴 단계에서 tasks.md는 수정하지 않았다.

## 후속 파일 상태 색상 검증

speckit-specify로 FR-011을 추가하고 speckit-clarify에서 표시용 S· 접두사를 제외한 실제 상태로 색상을 결정함을 명확히 했다. speckit-plan은 A 직접 비교가 S·A에서 실패하는 원인을 분석했고 speckit-tasks로 T019~T021을 정의했다. speckit-analyze에서 문서/작업의 모순·누락은 없었다. speckit-implement로 src/ui.rs의 file_status_color에서 A=기존 ACCENT, D=0xffa7b2, 나머지=기존 0xe6bc73을 사용하고 목록 상태 글자에 적용했다. Git/정렬/선택/표시 문자열은 유지한다.

상태 색상 테스트 1개가 통과하여 A/D/M/U/R/T와 Staged 쌍이 같고 삭제는 붉은색임을 확인했다. 최초 서식 검사에서 테스트 줄바꿈 차이를 확인해 cargo fmt로 정리한 뒤 cargo fmt --check를 통과했다. cargo clippy --offline --all-targets도 통과했다. 단순 색상 변경이므로 전체 테스트/배포 빌드는 반복하지 않았다. 실제 화면 확인과 실행 파일 교체는 수행하지 않았다.

speckit-converge에서 FR-011과 T019~T021을 코드에 대조했다. Staged 접두사 제외·삭제 붉은색·기존 나머지 색상이 명세와 일치하며 미해결 차이와 추가 작업은 없다. 수렴 단계에서 tasks.md는 수정하지 않았다. 별도 스크롤 문의는 읽기 전용으로 조사했으며 스크롤 코드를 변경하지 않았다.
