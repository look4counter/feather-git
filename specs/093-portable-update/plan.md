# 구현 계획 — 단일 실행 파일 업데이트

## 기술 맥락과 설계

- `src/ui.rs`의 환경설정 진입점 및 기존 GPUI 대화상자와 포커스 규칙을 재사용한다. `src/update_dialog.rs`가 조회·결과·다운로드·오류 상태를 관리하며 기존 백그라운드 실행기를 사용한다.
- `src/updater.rs`가 Cargo 빌드 버전, XML 및 HTTPS 다운로드를 처리한다. 기존 잠금 파일의 XML 파서와 시맨틱 버전 비교를 직접 사용하고 기존 HTTP 클라이언트를 재사용한다. 다운로드는 Feather Git 공식 GitHub 릴리스의 EXE 주소로 제한한다.
- 설치 파일과 같은 볼륨의 임시 디렉터리에 새 실행 파일과 현재 실행 파일의 도우미 복사본을 둔다. 도우미는 부모가 가진 파이프가 닫힐 때까지 대기하므로 정상 종료와 세션 저장이 마친 다음 교체한다. 새 파일 실행이 실패하면 도우미의 이전 파일을 원래 위치에 복원한다. 도우미 종료 후 새 앱이 임시 파일을 정리한다.
- 앱 시작에서 업데이트 도우미 인자를 먼저 분리한다. 이를 통해 도우미를 별도 배포하지 않고 현재의 단일 EXE 배포를 유지한다.

## 업데이트 확인 버튼 이동

- `src/settings.rs`의 공용 섹션 제목과 버튼을 재사용하고 Windows에서만 업데이트 요청 이벤트를 보낸다. Git 설정을 읽지 못해도 조회할 수 있다.
- `src/ui.rs`에서 요청을 받아 기존 업데이트 창을 환경설정 위에 표시하고 닫을 때 기존 포커스를 복원한다. 현재 패널, 하위 창, 저장 상태 및 중복 요청을 확인한다.
- 전체 대상 컴파일과 업데이트 테스트를 실행하고 환경설정의 새 진입점과 포커스 복귀를 검증한다.

## 헌장과 검증

헌장은 미작성 양식이다. 네트워크·파일 작업, 워크스페이스 UI, 시작 분기를 분리하고 Git 데이터나 기존 공개 파일 형식을 변경하지 않는다. XML, 버전 비교, 공식 주소 검증, 파일 교체와 복구를 자동 테스트하고 전체 대상 컴파일 및 릴리스 빌드를 실행한다.

## 업데이트 인증서 관리 계획

`src/settings.rs`에서 공용 목록·버튼과 Windows 파일 선택기를 사용한다. 목록 조회, 등록·삭제 및 입력 검사는 백그라운드에서 실행한다. `src/update_certificates.rs`는 사용자 경로에 CA 파일 내용과 표시 이름을 원자적으로 저장하며 목록 변경을 직렬화한다. `src/updater.rs`의 공용 HTTPS 클라이언트 생성에서 CA를 추가해 확인과 다운로드가 동일한 설정을 사용한다. 기존 HTTPS 검증과 배포 주소 제한을 보존하고 커밋을 생성하지 않는다.

## Windows TLS 검증 계획

Windows 대상에서 기존 HTTP 라이브러리의 네이티브 TLS 기능을 활성화한다. `src/updater.rs`와 `src/update_certificates.rs`에서 Windows TLS 백엔드를 명시하고, 버전 확인과 다운로드가 동일한 클라이언트 생성 함수를 사용하도록 유지한다. `src/avatar.rs`는 기존 Rustls 백엔드를 명시해 기능 활성화의 영향을 막는다. 주소 제한 및 서명·호스트 검증을 유지하고 전체 대상 검사, 관련 테스트와 빌드를 실행한다.
